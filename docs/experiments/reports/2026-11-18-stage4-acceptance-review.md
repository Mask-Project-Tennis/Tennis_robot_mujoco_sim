## 2. 合并前必须修复

### R1 · P1：发布节奏未受控制周期限制，步长限速可被高频调用绕过

- 位置：`src/real/unitree_r1d_interface.py:873–880`，重点 878–879；配套约束 `src/real/r1d_command_policy.py:579–603`。
- 触发：生产者以高于配置周期的频率提交目标，并允许发送线程逐个消费。
- 原因：`_decide` 发现 pending target 即返回 publish；`control_period_s` 在该调度中用于看门狗，不限制实际发布频率。策略却始终以 `dq_limit * control_period_s` 检查每帧步长。
- 确定性证据：冻结 fake clock 于 1000.0，周期为 0.002 s；依次提交 5 个每次递增 0.001 rad 的目标，每次等待发布完成。五帧均发布于 1000.0，说明一个周期内可累积多个允许步长。
- 影响：调用方频率或突发提交会改变实际目标变化速率，驱动提供的步长约束不能独立保证目标限速。
- 修复方向：建立实际发布期限并按绝对单调时钟调度；每个期限消费最新目标，避免积压追赶式连发。必要时按实际发布间隔复核目标变化率。
- 验收：高频生产者、同一时刻连续通知、调度延迟三类测试；周期未到不得多发，目标变化率不得因生产者频率提高而放宽。

### R2 · P1：急停登记后，尚未进入传输层的运动帧仍可发布

- 位置：`src/real/unitree_r1d_interface.py:982–989`；停止登记为 715–724。
- 触发：发送线程已取走目标、正在构造 active frame；另一线程登记急停。
- 原因：停止请求清空 pending target，但保持 phase=ACTIVE；发布前只检查 phase/generation，不检查停止请求或急停锁存。
- 确定性证据：在 `build_active` 返回前用 Event 暂停。确认急停已登记、`_emergency_latch=True` 且 `transport.publish_entered == 0`，再恢复发送线程，记录仍为 `['active', 'stop']`。这不是请求前已经进入 DDS 的在途帧。
- 影响：停止请求无法撤销已构造、尚未发布的运动目标，违反停止后的运动命令隔离要求。
- 修复方向：让停止登记与运动发布许可形成明确的互斥边界，撤销未获发布许可的 active frame；不能只增加另一个锁外布尔检查。
- 验收：覆盖构造前后、许可判定与传输调用边界，分别触发缓停、急停和故障停止；停止生效后不得新增未获许可的运动帧。

### R3 · P2：退权期间的急停升级丢失，原对象可以再次激活

- 位置：`src/real/unitree_r1d_interface.py:1154–1159`，以及最终状态转换 1238–1253。
- 触发：缓停已确认反馈，在 `release_control` 执行期间请求急停。
- 原因：退权前已读取 `_emergency_latch` 并缓存 `terminal_fault`；退权后收尾不重新合并急停锁存，还会清除锁存。
- 确定性证据：暂停 `release_control`，登记急停并确认 latch=True，再恢复；最终 `phase=READ_ONLY`、`fault_reason=None`、`stop_confirmed=True`。补入新鲜状态后，原对象 `activate()` 成功回到 ACTIVE。
- 影响：公开 `emergency_stop()` 的不可恢复语义被竞争窗口破坏。
- 修复方向：在提交终态的同一锁内读取并合并最终急停状态，终态 FAULT 不得降级为 READ_ONLY。
- 验收：退权开始前、执行中、返回后但终态尚未提交时的急停，均应得到 FAULT，并拒绝原对象再次激活。

## 6. 第二轮复验（2026-11-18，c65664f 之后）

migrate 建议"暂缓合并"：本地 main 可快进、六项修复已在分支上，但复验仍发现两项影响验收结论的问题。逐行核实**均属实**，处置如下。

### 复验-1（Blocking）发布限频与验收期限冲突

- 现象：驱动在上一帧 `publish` 返回后再等一个完整周期（`_next_publish_at = published_at + period`），而 CLI 把超期判据设为"相邻发送间隔 > 一个周期"（`publish_deadline_s = period`）。正常发布间隔恒为 `周期 + 发布/唤醒开销`，每次都被判超期；复验复现：周期 2 ms、模拟发送 20 µs → 三个间隔全部超期。端到端测试用 2× 周期作期限，未覆盖 CLI 的真实判定条件。
- 核实：属实。`compute_publish_interval_metrics` 的超期判据为 `interval > deadline + 1e-9`，与驱动"间隔 ≥ 周期"的调度语义数学上互斥——只要每次发布有非零开销，间隔必然略大于周期。
- 处置：不动驱动调度（保持"间隔 ≥ 周期、不补发"的安全不变量与步长限速前提），修正验收判据语义——**超期 = 错过半拍以上**：`interval > 1.5 × 期限`（`_PUBLISH_INTERVAL_OVERRUN_RATIO = 0.5`）。依据：发布开销是数十~数百 µs 量级，远小于半周期；真实漏拍（错过一个控制周期）表现为 ≈ 2× 期限，必然计入；原始 p50/p95/p99/max 仍全量落盘，判据收紧/放宽均可由原始值复核。该判据并非"放宽验收"：原判据"间隔 ≤ 一个周期"对任何 publish-then-rearm 实现都不可达，属于错误判据，而非可达能力的收紧。
- 回归：`test_publish_overhead_not_counted_as_overrun`（复验复现：2 ms + 20 µs → 0 次超期）、`test_publish_overrun_boundary`（1.25× → 0；1.5× 边界 → 0；1.55× → 1；2× → 1）；端到端 `_tracking_config` 的 `publish_deadline_s` 由 2× 周期改为 **1× 周期**，端到端用例从此覆盖 CLI 判定条件。旧码红线：6 failed / 4 passed。

### 复验-2（Blocking）同一反馈帧仍会重复计入跟踪误差

- 现象：`_pair_feedback_frames` 的样本行只带 `(received_at, q)`，配对按样本记录逐条消费。采样周期快于状态流时，连续两次采样读到同一缓存帧会产生两行，可分别被两条命令消费；复验复现：一帧反馈被计为两条命令都已匹配，夸大反馈覆盖率。
